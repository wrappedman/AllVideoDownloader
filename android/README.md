# All Video Downloader — Android

The Android app is the **same program** as the desktop app, re-hosted:

```
desktop (before)                          android (now)
─────────────────                         ─────────────
web/ (HTML/CSS/JS UI)                     web/  →  assets/web  (byte-identical copy,
                                                    loaded in a WebView)
FastAPI + WebSocket on 127.0.0.1:8000     Kotlin HTTP/WebSocket server on 127.0.0.1:<free port>
webfinder/core/*.py engine                com.allvideodownloader.avd.core.*  (port of the same modules)
pywebview window                          MainActivity WebView + __AVD_NATIVE__ bridge
yt-dlp/ffmpeg binaries in ~/bin           user-supplied binaries in the app's files dir (optional)
~/.avd/settings.json                      filesDir/config/settings.json
~/Downloads                               externalFilesDir/…/All Video Downloader (or a SAF folder)
```

Nothing in the repository root was removed or rewritten. The Android project lives
entirely in this directory, per the "separate directory/module" requirement.

## Why a Kotlin port instead of running the Python backend

The original backend needs CPython, `fastapi`, `uvicorn`, `httpx`, `yt-dlp` and a
full `ffmpeg`. None of those can be embedded without either a prebuilt Python
runtime (Chaquopy — needs the Google Maven repo) or per-ABI native builds of
ffmpeg/CPython. Both are hundreds of megabytes and neither is reachable from this
build environment. So `webfinder/core/*.py` was ported line-for-line to Kotlin,
and the *frontend* — where all the UI/UX lives — is shipped unchanged.

Behavioural parity was the goal, not a rewrite: the same REST routes, the same
JSON shapes, the same WebSocket events, the same site registry (384 recipes /
717 hosts / 10 families / 44 embed hosts, generated by `tools/gen_site_data.py`
straight from `webfinder/core/sites.py`), the same card kinds
(`media|hls|direct|page|webmedia|magnet|media_error`), the same job kinds
(`http|hls|ytdlp|sim`), the same KVS licence-code permutation, Dean-Edwards
unpacker, Aparat/Filimo adapters, cookie-source probing and yt-dlp CLI wiring.

## Android-specific adaptations (all intentional, all documented)

1. **FFmpeg / yt-dlp are optional, user-supplied.** Android cannot `pip install`.
   `Settings → FFmpeg path` / `System` still work; binaries placed in the app's
   files dir (`/data/data/com.allvideodownloader.avd/files/bin`) or on `PATH` are
   detected exactly as on the desktop.
2. **HLS is captured natively.** Without FFmpeg, `core/HlsCapture.kt` does the
   lossless job itself: variant selection, `EXT-X-MAP` init segments, AES-128 CBC
   decryption with per-segment IVs, TS concatenation, live-playlist notice.
   DASH and SAMPLE-AES say plainly that they need FFmpeg instead of failing obscurely.
3. **Download folder.** Default is app-specific external storage (no permission,
   visible over USB/MTP). If the user picks a folder with the system picker, they
   get a SAF *tree* URI; jobs are staged in the app cache (so Range/pause/resume
   keep working) and copied into the picked folder by `SafExport` on completion.
4. **Foreground service.** Downloads continue while the app is backgrounded
   (`DownloadService`, `dataSync` type, aggregate progress notification) — the
   phone equivalent of the desktop window staying open.
5. **pywebview bridge.** `ApiServer.bridgeShim()` injects `window.pywebview.api`
   with `minimize/toggle_maximize/close/pick_folder`, so `web/js/api.js` is
   untouched; `pick_folder` resolves asynchronously through the SAF picker.
6. **`system/selfupdate`** cannot pip-upgrade yt-dlp on Android, so it re-detects
   the engine and reports honestly what it found.
7. **`system/open-path`** uses an `ACTION_VIEW` intent through `AvdFileProvider`
   instead of `xdg-open`/`explorer`.
8. **No TLS impersonation.** `curl_cffi` does not exist here; `hasImpersonation()`
   returns `false` and the UI says so rather than pretending.
9. **Shared links.** `ACTION_SEND` text/plain is accepted and handed to the Direct
   tab, mirroring "paste a URL".

## Build

```bash
./build.sh                # -> build/AllVideoDownloader-debug.apk + artifacts/
./dev/run_tests.sh        # compile the engine for a desktop JVM and run the tests
```

`build.sh` drives `aapt2 → kotlinc → dx → apksigner` directly (the same four
steps the Android Gradle Plugin drives) because this sandbox has no Gradle
distribution and no Google Maven access. The sources are dependency-free
(`dependencies { }` in `app/build.gradle.kts` is deliberately empty), so nothing
is lost: a normal `./gradlew assembleDebug` builds the identical app wherever
Gradle + the Android SDK are installed.

Tool locations can be overridden: `KOTLIN_HOME`, `ANDROID_JAR`, `DX_JAR`,
`AAPT2`, `APKSIGNER`, `KEYSTORE`, `JAVA_HOME` (defaults live under `/tmp`).

## Tests

`dev/run_tests.sh` compiles `core/` + `api/` — which contain **no `android.*`
imports** — for a desktop JVM and runs two suites:

* `dev/JvmTests.kt` — 89 fixture checks ported from `tools/test_video_core.py`
  (HLS/MPD ladders, container sniffing, JSON, settings defaults, URL joining, the
  site registry, embed extraction, yt-dlp command construction) plus a live
  round-trip through the real HTTP/WebSocket server (index + shim injection,
  `/api/settings`, `/api/sites`, `/api/meta`, `/api/downloads`, 404s, path
  traversal refusal, `101` upgrade with the RFC 6455 accept key and the
  `bootstrap` event).
* `dev/DownloadTests.kt` — 47 end-to-end checks against a loopback HTTP server:
  direct download, 302 redirect follow, Range request/response, pause → resume
  with byte-identical output, native HLS capture (3 segments concatenated in
  order), AES-128 encrypted HLS decryption, DASH refusal message, and the job
  lifecycle (pause/resume/cancel/clear-finished, `to_dict` keys).

## What is *not* verified

There is no emulator, no `adb` and no Android device in this environment, so the
APK was **not** installed or launched. Verification of the artifact itself is
static: `aapt2 dump badging`, `apksigner verify` (v1+v2+v3), and an androguard
parse (valid APK, package/activity/service/provider, permissions, `resources.arsc`
tables). Everything that does not need Android framework classes — i.e. the whole
engine and the whole HTTP/WebSocket API — is executed for real by the suites
above. The remaining unverified surface is `MainActivity` (WebView + bridge),
`DownloadService`, `SafExport` and `AvdFileProvider`.
