# All Video Downloader — Android

The Android app is the **same program** as the desktop app, re-hosted:

```
desktop (before)                          android (now)
─────────────────                         ─────────────
web/ (HTML/CSS/JS UI)                     web/  →  assets/web  (byte-identical copy,
                                                    loaded in a WebView)
FastAPI + WebSocket on 127.0.0.1:8000     Kotlin HTTP/WebSocket server on 127.0.0.1:<free port>
webfinder/core/*.py engine                com.allvideodownloader.avd.core.*  (port of the same modules)
pywebview window                          MainActivity WebView + __AVD_NATIVE__ bridge
yt-dlp/ffmpeg binaries in ~/bin           user-supplied binaries in the app's files dir (optional)
~/.avd/settings.json                      filesDir/config/settings.json
~/Downloads                               externalFilesDir/…/All Video Downloader (or a SAF folder)
```

Nothing in the repository root was removed or rewritten. The Android project lives
entirely in this directory, per the "separate directory/module" requirement.

## Why a Kotlin port instead of running the Python backend

The original backend needs CPython, `fastapi`, `uvicorn`, `httpx`, `yt-dlp` and a
full `ffmpeg`. None of those can be embedded without either a prebuilt Python
runtime (Chaquopy — needs the Google Maven repo) or per-ABI native builds of
ffmpeg/CPython. Both are hundreds of megabytes and neither is reachable from this
build environment. So `webfinder/core/*.py` was ported line-for-line to Kotlin,
and the *frontend* — where all the UI/UX lives — is shipped unchanged.

Behavioural parity was the goal, not a rewrite: the same REST routes, the same
JSON shapes, the same WebSocket events, the same site registry (384 recipes /
717 hosts / 10 families / 44 embed hosts, generated by `tools/gen_site_data.py`
straight from `webfinder/core/sites.py`), the same card kinds
(`media|hls|direct|page|webmedia|magnet|media_error`), the same job kinds
(`http|hls|ytdlp|sim`), the same KVS licence-code permutation, Dean-Edwards
unpacker, Aparat/Filimo adapters, cookie-source probing and yt-dlp CLI wiring.

## The mobile UI

The frontend ships with a **CSS-only Android skin** (`mobile/mobile.css`), so the
desktop screens keep their layout while the phone gets a touch layout. Nothing in
`web/` changes: `tools/apply_mobile_ui.py` copies the folder and adds exactly four
lines to `index.html` (`class="android"`, the skin link, `viewport-fit=cover`,
theme colour). Every rule in the skin is scoped to `html.android`, and the skin
test fails the build if a single rule escapes that scope.

| desktop | phone |
|---|---|
| frameless window bar with minimise / maximise / close | top app bar: brand, connection dot, quit |
| 216 px icon rail on the left | bottom tab bar (Grab · Downloads · Settings), icon over label |
| speed widget + About + Exit at the rail foot | one compact floating cluster above the tab bar |
| hover-revealed row actions | always-visible 44 px action buttons |
| two-column settings, side-by-side analyse card | single column, chips scroll horizontally |
| centred dialogs | bottom sheets with a grab handle |
| 40 px buttons, 30 px icon buttons | 46 px buttons, 44 px icon buttons, 44 px switches |
| desktop scrollbars, hover transforms | no hover-stick, no scroll glow, `dvh` sizing, safe-area insets |

Android's back gesture is mapped to the existing UI: an open sheet closes (the
app's own Escape handler), a secondary tab returns to Grab, and only from there
does it leave the app — implemented in `MainActivity` without touching the
frontend or the engine.

Rebuild the asset copy after editing `web/`:

```bash
android/tools/sync_assets.sh      # web/ → assets/web + the Android skin
```

## Android-specific adaptations (all intentional, all documented)

1. **FFmpeg / yt-dlp are optional, user-supplied.** Android cannot `pip install`.
   `Settings → FFmpeg path` / `System` still work; binaries placed in the app's
   files dir (`/data/data/com.allvideodownloader.avd/files/bin`) or on `PATH` are
   detected exactly as on the desktop.
2. **HLS is captured natively.** Without FFmpeg, `core/HlsCapture.kt` does the
   lossless job itself: variant selection, `EXT-X-MAP` init segments, AES-128 CBC
   decryption with per-segment IVs, TS concatenation, live-playlist notice.
   DASH and SAMPLE-AES say plainly that they need FFmpeg instead of failing obscurely.
3. **Download folder.** Default is app-specific external storage (no permission,
   visible over USB/MTP). If the user picks a folder with the system picker, they
   get a SAF *tree* URI; jobs are staged in the app cache (so Range/pause/resume
   keep working) and copied into the picked folder by `SafExport` on completion.
4. **Foreground service.** Downloads continue while the app is backgrounded
   (`DownloadService`, `dataSync` type, aggregate progress notification) — the
   phone equivalent of the desktop window staying open.
5. **pywebview bridge.** `ApiServer.bridgeShim()` injects `window.pywebview.api`
   with `minimize/toggle_maximize/close/pick_folder`, so `web/js/api.js` is
   untouched; `pick_folder` resolves asynchronously through the SAF picker.
6. **`system/selfupdate`** cannot pip-upgrade yt-dlp on Android, so it re-detects
   the engine and reports honestly what it found.
7. **`system/open-path`** uses an `ACTION_VIEW` intent through `AvdFileProvider`
   instead of `xdg-open`/`explorer`.
8. **No TLS impersonation.** `curl_cffi` does not exist here; `hasImpersonation()`
   returns `false` and the UI says so rather than pretending.
9. **Shared links.** `ACTION_SEND` text/plain is accepted and handed to the Direct
   tab, mirroring "paste a URL".

## Build

```bash
./build.sh                # -> build/AllVideoDownloader-debug.apk + artifacts/
./dev/run_tests.sh        # compile the engine for a desktop JVM and run the tests
```

`build.sh` drives `aapt2 → kotlinc → dx → apksigner` directly (the same four
steps the Android Gradle Plugin drives) because this sandbox has no Gradle
distribution and no Google Maven access. The sources are dependency-free
(`dependencies { }` in `app/build.gradle.kts` is deliberately empty), so nothing
is lost: a normal `./gradlew assembleDebug` builds the identical app wherever
Gradle + the Android SDK are installed.

Tool locations can be overridden: `KOTLIN_HOME`, `ANDROID_JAR`, `DX_JAR`,
`AAPT2`, `APKSIGNER`, `KEYSTORE`, `JAVA_HOME` (defaults live under `/tmp`).

## Signing (when the Android build-tools are absent)

`build.sh` uses Google's `apksigner.jar` when it can find one, and otherwise
falls back to `tools/sign_apk.py`, which writes **APK Signature Scheme v2**
itself:

* **v2** — the APK Signing Block. The layout is the one AOSP's verifier walks:
  a length-prefixed *sequence* of length-prefixed signers → signed data
  (digests, certificates, attributes) → signatures → public key. The algorithm
  id in both the digest and the signature record is `0x0103`
  (RSASSA-PKCS1-v1_5 with SHA-256), which is what makes the content digest the
  chunked SHA-256 over the three sections (file contents, central directory,
  and the EOCD whose central-directory offset points at the signing block).

  Two things this got wrong at first, both fatal at install time: the outer
  "sequence of signers" length prefix was missing (Android then mis-parsed the
  signer and reported *"App not installed as package appears to be invalid"*),
  and the digest record carried `0x0101` (RSA-PSS) instead of `0x0103`.

* **v1** — optional (`tools/sign_apk.py --v1`), the JAR signature with
  `META-INF/AVD.SF` / `AVD.RSA`. Only Android 5–6 need it, and this build ships
  `minSdk 24`, so the platform verifies v2 alone: one fewer scheme to get wrong.

`tools/verify_apk.py` re-derives the content digest from the file and checks the
signature against the certificate's key, then (when `--v1` was used) re-checks
every `MANIFEST.MF` digest, the manifest digest in `CERT.SF` and the PKCS#7
signature. The build **fails** if verification fails. The verifier is itself
checked against a known-good APK produced by the real `apksigner` (it recomputes
that file's digest and accepts its signature), and the signature of every build
is additionally verified with `openssl dgst -verify`.

The signing key lives in `tools/debug-signing-key.DEBUG-ONLY.pem`: a
**debug-only** self-signed identity, committed on purpose so that every build of
this app shares one certificate (Android refuses an update signed by a different
key). It is not a release key and must never be used for one.

`minSdk` is 24 (Android 7.0). It was 21, but API 21–23 verify *only* the JAR (v1)
signature, and this repository has no `jarsigner` available to produce and
validate one — shipping an unvalidated v1 is what makes an install fail with no
useful message. If Android 5–6 support is ever needed, `tools/sign_apk.py --v1`
plus a `minSdk` bump back to 21 is the path, with a real device to test on.

The fallback needs one Python module that is not in the standard library:
`pip install cryptography`.

### Installing over an older build

Android only accepts an update signed with the certificate of the installed
copy. The pre-2.3.0 APKs were signed with a throwaway key generated in a `/tmp`
directory of a build machine, so that key is gone and **no new APK can ever be an
"update" for those installs** — uninstall the app, then install this one. From
`2.3.0` on the key is committed (`tools/debug-signing-key.DEBUG-ONLY.pem`), so
later builds keep updating in place. If a phone reports "App not installed" for a
*first* install, run `python3 tools/verify_apk.py <apk>`: it names the rejected
detail (signature, digest or alignment).

## What YouTube support really is

`core/Youtube.kt` talks to YouTube's own player endpoint, because the desktop
build's `yt-dlp` binary cannot run on Android. It walks a client ladder
(`ANDROID_VR` → `ANDROID` → `IOS` → `TVHTML5_SIMPLY_EMBEDDED_PLAYER` →
`WEB_EMBEDDED_PLAYER` → `MWEB` → `TVHTML5` → `WEB`, 25 s total), then the embed
page, then the watch page, and finally `core/YoutubeMirrors.kt` — public
Invidious/Piped front-ends that fetch the video from *their* addresses. That
last step is what makes a "Sign in to confirm you're not a bot" answer
survivable: the bot check is decided by the caller's IP, not by the app's code.
`tools.instances` is a plain list, so a dead mirror can be replaced without
touching anything else.

## Tests

`dev/run_tests.sh` compiles `core/` + `api/` — which contain **no `android.*`
imports** — for a desktop JVM and runs six suites (320 checks):

* `dev/JvmTests.kt` — 89 fixture checks ported from `tools/test_video_core.py`
  (HLS/MPD ladders, container sniffing, JSON, settings defaults, URL joining, the
  site registry, embed extraction, yt-dlp command construction) plus a live
  round-trip through the real HTTP/WebSocket server (index + shim injection,
  `/api/settings`, `/api/sites`, `/api/meta`, `/api/downloads`, 404s, path
  traversal refusal, `101` upgrade with the RFC 6455 accept key and the
  `bootstrap` event).
* `dev/DownloadTests.kt` — 47 end-to-end checks against a loopback HTTP server:
  direct download, 302 redirect follow, Range request/response, pause → resume
  with byte-identical output, native HLS capture (3 segments concatenated in
  order), AES-128 encrypted HLS decryption, DASH refusal message, and the job
  lifecycle (pause/resume/cancel/clear-finished, `to_dict` keys).
* `dev/PageTests.kt` — 51 checks on the reported bug "it finds the link but lists
  no qualities, so I cannot download": a local server serves a tube-style page
  whose player config holds the mp4 rungs, an HLS master, an `og:image` and ad
  noise. It asserts the page becomes a `webmedia` card with a labelled ladder,
  that **every** rung plans and downloads (the 1080 rung must be the exact file
  the page named), that opaque CDN hashes still get distinct names from their
  player slot (`video_url_high` → HD), that two slots meaning the same thing are
  told apart instead of rendering `MP4 | MP4`, that a page with no media returns
  an actionable `media_error` card (reason + phone-specific guidance) instead of
  a dead "found it" card, and that a raw mp4 still produces a one-click `direct`
  card.
* `dev/YoutubeTests.kt` — 54 checks on the YouTube path, which on desktop was
  yt-dlp's job. A local server answers `/youtubei/v1/player` with the same JSON
  the real endpoint returns, and the suite asserts: every link shape resolves to
  a video id; the card carries the video's real title and a ladder ordered
  muxed → video-only → audio; the chosen rung plans to a plain http download
  under the right filename and the file on disk is byte-exact; a playability
  refusal ("Video unavailable") and a cipher-only answer each become a
  `media_error` card that says so instead of a dead end; a refused API still
  recovers from the watch page's own URLs; a page full of script noise
  (`persist_identity`, `generate_204`, `m_base`) yields no junk rows; and the
  exact answer a VPN user gets — "LOGIN_REQUIRED — Sign in to confirm you're not
  a bot" — ends in a real ladder borrowed from a mirror (which downloads), or,
  when the mirrors refuse too, in a card that names the bot wall, says the VPN
  is the thing to change and that the mirrors were tried. The embed-page route
  and the cookies.txt header (only the matching host's cookies) are covered too.
* `dev/ui/css_check.mjs` — 27 checks on the Android skin: it must parse cleanly,
  every rule must stay scoped to `html.android` (i.e. the desktop UI cannot be
  affected), the tab bar must be fixed to the bottom with content padded clear of
  it, touch targets must meet 44 px, dialogs must present as bottom sheets, and
  no frontend script may branch on being on Android.
* `dev/ui/ui_test.mjs` — 52 checks that load the **real, unchanged `web/`
  frontend** in jsdom against the real API server: shell/nav rendering,
  settings cards fed by `/api/settings`, a settings change round-tripping
  through `PUT`, websocket bootstrap, analyze of a live URL, click-to-download
  → the job row appearing in the Downloads view with the file landing on disk
  byte-for-byte, an HLS ladder, and the full page path (page URL → quality chips
  → download → finished job) — plus the skin measured on the live DOM
  (computed layout of every landmark, and all 174 skin selectors resolving to
  real elements). Needs `npm install` once in `dev/ui/` (jsdom, ws, css-tree);
  the suite is skipped when those are absent.

## What is *not* verified

There is no emulator, no `adb` and no Android device in this environment, so the
APK was **not** installed or launched, and `MainActivity` / `DownloadService` /
`SafExport` / `AvdFileProvider` were not executed on Android. For the same reason
the mobile layout was validated structurally (CSS cascade resolved per element,
layout invariants asserted, every selector checked against the booted DOM) — it
has **not** been pixel-rendered: this sandbox has no browser engine (Chromium
needs libnss/libnspr, which are not installable here). Verification of the artifact itself is
static: `aapt2 dump badging`, `apksigner verify` (v1+v2+v3), and an androguard
parse (valid APK, package/activity/service/provider, permissions, `resources.arsc`
tables). Everything that does not need Android framework classes — i.e. the whole
engine and the whole HTTP/WebSocket API — is executed for real by the suites
above. The remaining unverified surface is `MainActivity` (WebView + bridge),
`DownloadService`, `SafExport` and `AvdFileProvider`.

One more honest limit: this sandbox has no route to `youtube.com`, so the
YouTube extractor (`core/Youtube.kt`) was validated against the player API's
schema on a local fixture server, **not** against a live response. YouTube gates
its player per client, per region and per video, and can start demanding a
bot-check token at any time; the client ladder (`ANDROID_VR` → `ANDROID` → `IOS`
→ `WEB`) plus the watch-page fallback exist for exactly that, and when all of
them are refused the app says why instead of printing junk.
